# 教程 15：严格漏斗分析（用户 + 商品 + 时间顺序）

## 目标

在 DWD 明细上验证真正的行为链路：

```text
pv -> fav/cart -> buy
```

观察粒度是 `user_id + item_id`，不是全表行为总数。每一步都要求事件时间不早于前一步。

## 为什么不能直接相除

`buy_count / cart_count` 只是行为数量比，可能来自完全不同的用户和商品，也没有时间顺序。严格漏斗必须证明同一个用户在同一个商品上先发生浏览，再发生收藏/加购，之后发生购买。

## SQL 分解

1. `first_pv`：每个用户商品对的首次浏览时间；
2. `first_intent`：在首次浏览之后最早的收藏或加购时间；
3. `first_buy`：在意向事件之后最早的购买时间；
4. `user_item_funnel_stage`：保存每个阶段时间和 0/1 标记；
5. `strict_funnel_summary`：统计用户商品对、去重用户和阶段转化率。

## 时间口径

时间戳是秒级。同一秒无法判断真实先后，因此采用 `>=`。本样本实测成功衔接中没有同秒 `pv -> intent` 或 `intent -> buy`，但生产方案仍应记录这一风险。

## 本地精确基线

| 阶段 | 用户商品对 | 去重用户 |
|---|---:|---:|
| PV | 691,122 | 9,621 |
| PV 后收藏/加购 | 11,101 | 4,910 |
| 意向后购买 | 1,023 | 865 |

| 指标 | 结果 |
|---|---:|
| PV -> 意向 | 1.6062% |
| 意向 -> 购买 | 9.2154% |
| PV -> 购买 | 0.1480% |

Hive 结果应与该基线一致。若不一致，先检查是否误用了事件随机 1M 表、是否忘记按 `user_id + item_id` 连接，以及是否把异常时间带入计算。

## 实际构建耗时

本次严格漏斗构建耗时：`32.887 seconds`。该时间包含三阶段聚合、用户商品键连接、阶段表 ORC 写入和汇总表写入。
