# 教程 16：用户留存分析

## 口径

- 分析对象：用户级 DWD 有效明细；
- cohort_date：用户第一次发生任意有效行为的日期；
- day_0：首日活跃用户；
- day_1/day_2/day_3/day_7：首日之后第 1/2/3/7 天再次活跃的用户；
- 活跃定义：当天有任意 `pv/fav/cart/buy`，不要求再次购买。

先按 `user_id + dt` 去重，再计算日期差，否则同一用户一天多条行为会重复计数。构建脚本使用嵌套子查询以兼容当前 Hive 3.1.3 的 `INSERT` 语法。

## 为什么只看 day_7 需要谨慎

本项目业务范围是 2017-11-25 至 2017-12-03。较晚 cohort 没有完整的第 7 天观察窗口，因此 day_7 为空或偏低不等于用户质量差，属于右删失问题。解释时要标注观察窗口是否完整。

## 输出

- 阶段明细：`ecommerce_ads.user_retention_stage`；
- cohort 汇总：`ecommerce_ads.user_retention_summary`。

## 验收

- `stage_users=9659`；
- cohort 日期范围：`2017-11-25` 至 `2017-12-01`（之后两天仍有活跃，但没有用户首次活跃）；
- `invalid_retention_rows=0`；
- 任意留存人数不超过 cohort 用户数；
- 结果按 cohort_date 输出，便于制作留存矩阵。

## 实际运行记录

- 首次执行：Hive 3.1.3 无法解析 `INSERT OVERWRITE TABLE` 后直接跟 `WITH` 的写法，在编译阶段失败，未写入结果；
- 修正：改用等价的嵌套子查询，留存口径不变；
- 修正后构建耗时：`55.312 seconds`；
- 写入方式：`INSERT OVERWRITE`，重复执行不会累加重复结果。

## 时区修正

首次结果出现 `cohort_date=2017-11-24`。诊断证明 Hive/JVM 默认按 UTC 执行 `from_unixtime`：时间戳 `1511539200` 被转换为 `2017-11-24 16:00:00`，而上海时间应为 `2017-11-25 00:00:00`。

DWD 已改为显式使用 `from_utc_timestamp(event_ts * 1000, 'Asia/Shanghai')`，并重新生成日期分区。留存结果必须在修正后的 DWD 上重建。

正确留存阶段表基线：68,330 个用户日期组合、9,659 个用户、7 个 cohort 日期。

修正后实际运行：构建 `56.761 seconds`，验收 `52.792 seconds`。所有验收通过，错误的 `2017-11-24` cohort 已消失。

`2017-11-25` cohort：6,998 人；D1 5,483（78.3510%）；D2 5,392（77.0506%）；D3 5,295（75.6645%）；D7 6,904（98.6568%）。D7 高于 D1 不矛盾，因为这里统计指定第 N 天活跃，并不要求连续活跃。
