# 教程 12：用户级抽样与严格漏斗准备

## 为什么不能直接使用 1M 事件随机样本

现有 `user_behavior_1m.csv` 对一亿条事件做等概率事件抽样，适合估计行为分布并开发按日指标，但它会随机丢掉同一用户的大部分其他事件。

本地严格漏斗试算结果为：

- 有浏览的用户商品对：891,807；
- 浏览后再收藏或加购的用户商品对：185；
- 上一步之后再购买的用户商品对：1。

这主要反映事件抽样破坏了序列，不能解释为真实电商漏斗极差。

## 新抽样单位

新脚本按 `user_id` 做固定哈希抽样，名义抽样率为 1%。一旦某个用户入样，就保留该用户在源文件中的全部事件。

这样能够保留：

- 同一用户的行为先后顺序；
- 同一用户对同一商品的多次行为；
- 用户级留存、复购和 RFV 计算所需的连续记录。

抽样规则使用固定 seed 和确定性 64 位混合哈希。同一源文件、相同参数会得到相同结果。不要使用 Python 内置 `hash()`，它的结果可能因进程而变化。

## 严格漏斗口径草案

观察单位为 `user_id + item_id`：

1. 找到首次 `pv`；
2. 找到不早于首次 `pv` 的首次 `fav` 或 `cart`；
3. 找到不早于上一步的首次 `buy`；
4. 分别统计进入每一步的用户商品对和去重用户。

时间戳只有秒级。同一秒内无法证明真实先后，因此采用 `后一步时间戳 >= 前一步时间戳`，并单独统计同秒衔接数量作为口径风险。

## 输出隔离

- Windows 文件：`data/sample/user_sequence_1pct.csv`
- 清单：`docs/user_sequence_sample_manifest.json`
- 后续 HDFS：`/warehouse/ecommerce/ods/user_sequence_1pct`

该样本不会覆盖已有 10K 和 1M 事件样本。

## 实际生成结果

- 源文件行数：100,150,807；
- 用户级样本行数：976,621；
- 完整入样用户：9,660；
- 非 5 列记录：0；
- 文件大小：35,799,859 字节；
- SHA-256：`7d61da1c410720c3a3c31926f390c543e2e594761954abf6f80c045bf9c4c67f`；
- 生成耗时：约 327.3 秒。

有效业务范围内有 976,097 行；范围前异常 506 行，范围后异常 18 行。ODS 仍保留全部 976,621 行，DWD 再隔离 524 条异常。

## 严格漏斗本地基线

以 `user_id + item_id` 为单位，使用不递减时间顺序：

| 阶段 | 用户商品对 | 去重用户 |
|---|---:|---:|
| 已浏览 | 691,122 | 9,621 |
| 浏览后收藏或加购 | 11,101 | 4,910 |
| 上一步后购买 | 1,023 | 865 |

- 浏览对到意向对：1.6062%；
- 意向对到购买对：9.2154%；
- 浏览对到购买对：0.1480%；
- 同秒 `pv -> intent`：0；
- 同秒 `intent -> buy`：0。

与事件随机 1M 样本相比，用户级样本保留了大量可衔接序列，适合后续严格漏斗、留存、复购和 RFV 专题。
